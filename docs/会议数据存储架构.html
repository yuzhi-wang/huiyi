02数据存在哪里

数据存储方式说明
录音文件OSS + audio_url文件上传 OSS，数据库保存永久 URL。
会议基本信息明确类型的字段会议 ID、标题、客户、创建时间、时长、处理状态等。
会议摘要TEXT直接保存正文，便于展示和编辑。
转写全文（如需要）TEXT30 分钟会议的文本量通常可直接入库，无需仅因时长而文件化。
关键事项JSONB保存结构灵活的列表或对象，例如客户需求、结论、待确认问题。
待办事项独立表、独立字段内容、负责人、截止时间、完成状态，支持单独查询和更新。

类型选择：固定业务属性使用明确类型的字段；正文使用 TEXT；结构灵活的内容使用 JSONB。三者都存放在 PostgreSQL 表中。

03文件与配置的分工

会议业务表保存 URL

录音使用永久 URL 关联，不需要在会议表里重复保存 Bucket、域名等存储配置。

统一维护 OSS 配置

沿用 freshstack-cloud 的文件模块：Bucket、域名、Endpoint 等由文件配置维护；configId、path 由文件记录维护。

已有配置位于 infra_file_config，文件记录位于 infra_file。存储配置中的凭据仅由后端使用。

04基础处理流程

  1. 录音结束后上传 OSS，将返回的永久 URL 关联到会议记录。
  2. 后端在后台处理录音，生成摘要、关键事项和待办；有全文需求时增加转写。
  3. 将处理结果写入 PostgreSQL，更新会议处理状态。
  4. App 查询会议内容，使用录音访问地址回放；失败时保留录音，支持重试。

05后续扩展：pgvector

在现有 PostgreSQL 中增加语义检索能力。有跨会议搜索、历史会议问答需求时再接入，无需另建独立向量数据库。

例如：搜索“客户认为价格偏高”，可以找到“这个报价超预算了”等语义相关的会议片段，并关联录音时间位置。

  1. 准备数据：转写全文切成片段，由 embedding 模型生成向量。
  2. 保存与检索：PostgreSQL 保存片段、会议 ID、时间位置和向量，pgvector 负责向量相似度检索。
  3. 返回结果：展示相关原文和录音位置；需要问答时，再由大模型基于检索结果生成回答。

接入前确认线上 RDS 的 PostgreSQL 版本、可用 vector 扩展及账号权限。向量维度与 embedding 模型保持一致，索引按数据量和性能需求配置。录音仍存 OSS，摘要、全文和待办沿用当前存储方式。

本页仅用于架构展示，不连接数据库、OSS 或模型服务。基础方案与 pgvector 扩展均为设计说明，不代表已实施。完整逐字稿的生成能力按后续需求确定。
