## 1. 开工结论

可以按原需求开始技术验证，但不能直接以 `uni.getRecorderManager().start({ duration: 1800000, encodeBitRate: 24000 })` 和 `uni.request({ enableChunked: true })` 作为已成立的 Android 实现。

当前官方文档给出的关键限制是：

- uni-app 录音 `duration` 最大 600000 ms（10 分钟）；`encodeBitRate`、`numberOfChannels` 参数标为仅小程序支持。[D1]
- 经典 uni-app 的 `uni.request.enableChunked` 标为微信小程序；没有据此确认 Android App 的增量回调能力。[D2]
- HTML5+ 的 `plus.net.XMLHttpRequest.responseText` 明确支持在 readyState 3 读取已接收的部分数据，可作为 Android 流式接收的首选验证对象；真机是否及时分发仍未验证。[D5]
- 阿里云当前仍明确 `qwen3.5-omni-plus` 支持最长 3 小时音频，Base64 字符串必须小于 10MB；北京示例使用含 Workspace ID 的业务空间域名。[A1]

建议首阶段路线：**经典 uni-app + Vue 3 + JavaScript 页面，Android 录音用薄层 Native.js / MediaRecorder 适配，文件保存在应用私有目录，模型通过 plus.net.XMLHttpRequest 直接 HTTPS POST，手工解析 SSE。** 不增加后端、OSS、独立 ASR 或自动音频切分，也不更换模型。

这里的“建议”是基于 API 文档的实现路径，不代表上述组件组合已经通过 Android 真机验证。首先完成本文第 6 节的技术门槛，再完善业务页面。

### 打包方式与账号要求补充

原需求优先云打包，所以上表围绕云打包准备。Android APK 本身并不要求 DCloud 账号；普通原生 Android 项目可以在本地构建和签名。

但本项目采用经典 uni-app，其 Android App 使用 DCloud 运行时。官方离线 SDK 从 **3.1.10** 起要求配置 AppKey；需登录 DCloud 开发者中心，在应用的“各平台信息”创建离线 AppKey，且 **DCloud AppID、Android 包名、签名证书 SHA1** 必须与申请信息一致。因此“离线打包”表示 APK 在本机编译，不代表完全不需要 DCloud 初始化配置。[D9][D10]

- 云打包：使用 DCloud 云端构建服务，准备 DCloud 账号、AppID、包名及签名配置。
- 本地离线打包：准备匹配版本的离线 SDK、本地 Android 构建环境、包名及签名，并预先申请/配置离线 AppKey；APK 构建过程在本机进行。
- Android 签名证书可以在本地生成；DCloud 的 AppID/AppKey 与阿里云 API Key 是不同用途的标识，不能互相替代。

账号/AppKey 是所选 DCloud 工具链的要求，不是会议录音功能或 Android 安装 APK 的通用要求。当前未切换原需求中的优先云打包路线。

## 4. 关键技术核查与最小方案

### 4.1 30 分钟录音

**事实与边界**

`uni.getRecorderManager()` 支持 App，但参数文档将 duration 上限写为 10 分钟，码率和声道参数标为仅小程序；暂停、恢复、分帧回调也不支持 App。onStop 中 duration / fileSize 标为支付宝特定版本支持，Android 不应直接依赖这两个返回字段。[D1]

同页下方“编码格式与采样率、码率关系”又提到 Android/iOS，与参数平台列存在不一致。这不能证明 Android 的 encodeBitRate 已生效，更不能把传入 1800000 当成已支持 30 分钟。

HTML5+ `plus.audio` 文档列出 Android AAC 支持，但 supportedFormats / AudioRecorderStyles 段落仍保留 AMR/3GP 描述；没有明确的 bitrate 参数。它适合做能力探测，不能当作可控低码率长录音的既定方案。[D4]

**推荐验证实现**

在 `services/recorder.android.js` 内使用 `plus.android` 桥接系统 `android.media.MediaRecorder`。Native.js 官方允许直接导入 Java 类并调用 Android API；页面仍是 JavaScript，不要求新建服务端或迁移 uni-app x。[D6]

候选参数与顺序：

1. 声明并请求 `android.permission.RECORD_AUDIO`；权限拒绝时不进入录音状态。Native.js 的 requestPermissions 返回 granted / deniedPresent / deniedAlways。[D6]
2. 建立 MediaRecorder（根据目标 Android API 处理 Context 构造器），设置 MIC → AAC_ADTS 输出格式 → AAC 编码器 → 单声道、16000 Hz、24000 bit/s 候选码率。
3. 指定私有目录内唯一文件名，配置最大约 1800000 ms，注册错误/时长通知，prepare → start。每次只允许一个录音实例。
4. 停止后释放录音资源，再检查文件、媒体时长和大小。时长通知与手工停止可能竞争，必须保证停止/保存只执行一次；Android 文档明确时长到达后的停止是异步的。[N1]
5. 如果 24 kbps 听感不足，再对照测试 32 kbps；不静默转用高码率或更改格式后缀来伪装编码。

Android 官方明确 setAudioEncodingBitRate 的请求值可能被平台调整，采样率也受格式和设备限制。[N1] 因此记录“请求参数”和“实际结果”两组数据。AAC_ADTS、实际时长读取、长录音稳定性以及低码率中文会议听感都必须真机验证。

如 Native.js 构造器、线程或事件桥接不稳定，最小后备是把同一段 Android 录音能力封装为本地 UTS/原生插件供 JS 调用；它增加端内模块及自定义基座验证，不扩大业务架构。只有首选路径被实测阻断后再细化该后备实现。

### 4.2 持久保存、读取与内存

- 文件保存在应用私有文档目录；Native recorder 可先写唯一临时名，停止并校验后移入 `_doc/meetings/`。若使用 uni recorder，`uni.saveFile` 支持 App，成功后临时路径已失效，必须保存返回的 savedFilePath。[D3][D8]
- 先持久保存音频，再写记录索引；保存失败不能显示“已保存”。不要把音频或 Base64 写入 uni storage。
- 保存 `id / createdAt / customerName / audioPath / durationMs / sizeBytes / status / failure / result` 即可；小规模 Demo 使用简单本地记录存储。重新启动时重新解析路径并校验文件。
- App 文件读取首选 `plus.io.resolveLocalFileSystemURL` → File → FileReader.readAsDataURL；从结果中分离 Base64，并按已验证的真实音频格式构造 API data。不能直接照搬 Node.js fs/Buffer。[D8]
- 实际时长优先读媒体元数据或播放器的有效时长，并与墙钟计时和回放交叉验证；计时器只用于 UI。若元数据读取失败，明确标记待验证，不伪造实际时长。

**提交前大小校验**

设原文件大小为 N 字节，则 Base64 字符数为 `4 * ceil(N / 3)`。Base64 是 ASCII，这同时是其 UTF-8 字节数。先用文件大小判断是否超限，避免为已知超限文件分配大字符串；读取后再检验实际长度。

官方写“必须小于 10MB”，未在所读段落区分 MB / MiB。本 Demo 建议保守取 `10_000_000` 字节，并使用严格 `<`。理论最大原文件为 7,499,997 字节；不能写成“小于等于 7.5MB”。再保守检查最终 UTF-8 JSON 请求体低于 10,000,000 字节，这属于 App 余量策略，不冒充官方整包大小规定。[A1]

| 30 分钟候选 | 理论原文件 | 理论 Base64 | 判断 |
| --- | --- | --- | --- |
| 24 kbps | 5,400,000 B | 7,200,000 B | 首选验证；另加容器/帧头开销 |
| 32 kbps | 7,200,000 B | 9,600,000 B | 余量仅约 4%，实际编码和封装开销可能接近或越过限制 |
| 64 kbps | 14,400,000 B | 19,200,000 B | 不满足整段 Base64 提交 |

建议以 Base64 约 9MB 以下作为调参目标，不把目标值冒充服务硬限制。超限要保留文件、允许回放，提示“当前录音超出整段分析大小限制”；不截断、不切分、不自动转码。

7.2MB 的 Base64 在 JS 引擎中可能占约 7.2–14.4MB，Data URL、JSON 序列化、桥接和 HTTP 发送还可能产生副本。不能把网络载荷大小当成峰值内存。只允许一条生成任务；Base64 不进入 Vue 响应式状态、日志或记录索引；请求结束即释放引用。必须测真机编码/序列化耗时、进程内存与 UI 响应。

### 4.3 HTTPS 与流式文本

首选 `plus.net.XMLHttpRequest`：POST、Authorization Bearer、Content-Type application/json、responseType text；保留正常 TLS 校验。官方说明 readyState 3 的 responseText 是已接收的部分文本，状态 4 是完整响应，也提供 onprogress。[D5]

实现应维护 `consumedLength`，从累计 responseText 提取新增内容，在 onprogress / onreadystatechange 中交给同一解析器，状态 4 再排空尾部。不能每次把累计 responseText 全量重复追加，也不能把网络回调边界当作 SSE 事件边界。

SSE 解析器需要处理：跨回调半行、LF/CRLF、空行分隔、多 data 行、注释行、同一回调多个事件、JSON 分片、空 choices 的 usage 帧、服务错误事件。只把 `choices[0].delta.content` 纳入候选纪要。

完成门槛应包括 HTTP 成功、正常流结束、业务 finish_reason 正常、结构解析和校验通过、结果落盘成功。预期 OpenAI 兼容 SSE 有 `[DONE]` 终止；本次指南示例显示 finish_reason=stop 和 usage 帧，但未完整展示 `[DONE]`，因此在首次真实流中确认终止约定后固化。默认保守要求终止标记；如果该接口实测以正常 EOF + stop 结束，需有官方协议依据和回归样例再调整。仅收到一个可解析 JSON 或触发 HTTP success 不能提前成功；length、异常断连、缺少结束证据都进入可重试失败。

设置连接/整体/空闲超时和主动 abort，重试仅由用户点击触发；避免自动重试导致重复付费。若当前 Android 构建实际只在结尾回调，不能将“流结束后一次显示”冒充流式完成，应验证最小端内原生网络适配；不引入代理后端。

### 4.5 结果与状态

建议最小结果结构为 `summary: string`、`keyPoints: string[]`、`todos: [{ content, owner, dueDate }]`。owner / dueDate 未明确时为 null，todos 可为空。提示词明确：只依据音频、区分询问/提议/确认、变更采用最终确认、矛盾和听不清标为待确认，不补写金额、交期、负责人或承诺。

仅在流结束后解析候选结果，允许剥离完整的代码围栏，不用正则从截断内容拼凑成功 JSON。检查字段类型、必填内容、空待办语义；解析失败保留音频和可理解的原因。结构校验不能证明事实准确性，金额/数量/承诺仍需人对照录音验收。

状态建议：`recording → saving → saved → validating → generating → succeeded`；失败分 `save_failed / input_invalid / too_large / api_failed / stream_incomplete / parse_failed / persist_failed`。只有原音频与结果均成功保存才显示生成成功。启动时将残留 generating 标为“上次生成中断，可重试”，不自动再次提交；已完成旧结果不被失败重试覆盖。

## 6. 首阶段验证方案

所有实际执行证据填写到《首阶段验证记录.md》，当前均为未执行。

1. **环境门槛**：记录 HBuilderX/编译器/基座版本、手机型号、Android 版本、内存、App 版本；确认 IDE 可识别手机。验证首次授权、拒绝后重试、永久拒绝提示。
2. **短录音**：分别录 10 秒、1 分钟；设置 16kHz/mono/AAC/24kbps，检查文件实际编码、容器、大小、时长，回放开头/中间/结尾。立即停止、重复停止和录音失败不能产生假成功。
3. **持久性**：无 Key、离线录音；停止保存后完全退出再开，能查看和播放。索引引用持久路径；保存失败、文件为空/缺失有独立提示。
4. **长录音**：前台连续约 30 分钟，开头/中段/结尾录入可辨认时间标记；核实跨过 10 分钟无自动结束、末尾完整、实际时长与墙钟相符。记录请求/实际码率和编码后长度；候选 32kbps 仅在需要改善听感时追加对比。
5. **内存与超限**：对实际长文件读 Base64 并构造请求但不发出；记录前后进程内存、耗时、UI 卡顿、清理后的状态。用固定离线样例验证 `4*ceil(N/3)`、严格边界、空文件、超限拒绝；每种失败后音频仍可播放。
6. **流解析离线用例**：逐字/多事件切片、中文 UTF-8 跨字节（针对字节型后备实现）、LF/CRLF、注释、多 data 行、usage 空 choices、缺少完成标记、finish_reason=length、非 JSON 和合法但字段错误。网络完成前不得写 succeeded，落盘失败也不得 succeeded。
7. **真机流传输验证**：可用仅含固定合成数据的临时测试 SSE 端点验证 POST、增量到达与断流；这只是开发测试设施，不成为 Demo 运行依赖，也不接收 Key 或会议录音。若不建立测试端点，则在 P2 短音频真实调用中验证传输，不能以离线解析测试代替网络验证。
8. **P2 首次真实调用**：另行在获准的测试阶段执行；本次不调用。App 内填 Key/Workspace ID；短音频先验证 endpoint、format、首个 delta、stop/终止事件及实际 usage；清除 Key 后历史结果仍能看。然后长音频验证金额、数量、交期、提议被否决、负责人/日期缺失及无明确待办。
9. **异常与重试**：缺 Key、本地模拟无效权限/限流、断网/超时/中断、解析失败、重复点击；真实环境按必要性验证，不为凑覆盖重复付费。失败保留文件；手动重试只生成一个请求。
10. **最终复验**：云打包的独立 APK 安装后重复 30 分钟录音、真实整段提交、流式与异常、重启历史。浏览器预览和基座运行均不能替代该项。

首阶段退出标准：环境可运行；长录音实际满足时长、质量、文件大小；持久化和 Base64 内存可接受；SSE 解析和传输各有证据。任一关键点失败，先记录具体接口/版本/设备及最小修复路线，再进入下一阶段，不把未测项标成通过。
